## 一之二、这份数据该建在哪一级（一条判断法）

初始化最容易出错的地方不是「建没建」，而是「建在哪一级」。建错层级的症状
往往**不报错**：页面照常打开，只是数据对不上、换个客户就没了。

三层，只问一句话：

> **「这个东西会不会被第二个客户 / 第二台设备用到？」**

| 层级 | 判断 | 典型对象 | 谁继承 |
| --- | --- | --- | --- |
| 系统级 | 平台自带，与租户无关 | 部件库、语言包、系统规则链 | 全部租户 |
| **租户级（模板）** | 会复用，改一次应全部生效 | 参数字典、资产档案、设备档案、厂商型号、分时方案、**挂在设备档案上的告警规则与计算字段** | 该租户下全部客户 |
| **客户级（实例）** | 有明确归属：某客户、某场站、某台设备 | 场站、分项、设备、遥测、看板副本、客户菜单 | 只有该客户 |

**会 → 租户级，建一次；不会 / 有归属 → 客户级，跟着客户建。**

### 四个踩过的坑（照着反例记）

- **告警规则建在设备上** → 换一台表就没了，第 21 台表没有人管。
  正确：建在**设备档案**（`DEVICE_PROFILE`）上，同档案设备自动继承。
- **资产档案等到用到才建** → 漏建时 `assetProfileId` 写 null 也不报错，
  页面照常渲染，但按档案筛选、模板、统计全空。
  正确：建租户时**一次建全 13 个**，之后所有路径只查不建。
- **分类树根建在每个客户下** → 20 个客户 20 套根，报表无法横向汇总。
  **现状**：4 棵根仍建在客户级（`customer_id` = 该客户），每个客户一套。
  改造方向是把根提到租户级（`customer_id` = NULL）、客户只挂子节点 ——
  **尚未实施**，属已知待办；现阶段客户数少，不影响使用。
- **计算字段建在具体设备上** → 新建的表没有派生指标。
  正确：`calculated_field` 的 `entity_id` 写 **DeviceProfileId**，这是 TB 里
  唯一能让「模板 → 实例」自动生效的形态。

### 一个例外：重名

资产名、设备名在**租户内**唯一（唯一键是 `(tenant_id, name)`，不是客户内），
所以两个场站各有一台「1#进线总表」会撞键。
解决办法是**展示用 `label`、唯一用 `name`**：`name` 加场站前缀（如 `单相园-1#进线总表`），
`label` 留业务原名。前端渲染一律取 `label || name`。
这属于命名约定，不改变「场站/设备是客户级实例」的定位。

## 一之三、装完第一件事：打开「平台自检」

**路径**：租户管理员 → Platform → 平台自检；客户用户 → 设备运维 → 平台自检。

这一页把上一张清单里的每一项**逐条数一遍**，给出四类状态：

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| 正常 | 数量达标 | 不用管 |
| 不完整 | 有，但数量不足 | 功能能跑，报表会缺角 —— 按提示补 |
| 缺失 | 完全没有 | 对应功能不可用 —— 按提示补 |
| 可选 | 暂时不需要（如演示数据已清） | 不用管 |

每一条都带三样东西：**缺了会怎样**、**怎么补**、**看手册哪一页**。
顶部横幅一眼看出整体健康度：全绿才算初始化完整。

> 为什么值得先看这一页：初始化缺项**不会报错**。
> 页面照常打开、按钮照常能点，只是某些报表空白、某些统计为 0。
> 不看自检，往往要等到客户提问才发现缺东西。

## 一之四、演示数据：生成、清除、换成自己的

新客户建出来时带一套演示数据（2 个场站、21 台设备、14 天遥测），
目的是**装完就能看到完整效果**，不用等 RTU 接入。

但它只是样板。接入真实设备后的正确做法是：

1. 先按[设备接入](/admin/device-access)把 RTU 接上，验一条数据能上报
2. 打开客户 → 设备运维 → **平台自检** → 「清除演示数据」
3. 按自己的业务建场站 → 分项 → 设备 → 拓扑

**清除只删带 `demo` 标记的实体**，你自己建的东西一个都不动。
清错了也没关系：同一页有「生成演示数据」，可随时重建（幂等，已存在则跳过）。

| 操作 | 页面 | 命令行 |
| --- | --- | --- |
| 看数量 | 平台自检 → 演示数据 | `GET /api/energy/demo-data` |
| 生成 | 点「生成演示数据」 | `POST /api/energy/demo-data` |
| 清除 | 点「清除演示数据」 | `DELETE /api/energy/demo-data` |

## 三、能源参数字典（字段定义）

这是**全平台的数据字典** —— 设备上报的键名必须与它一致，否则存不进去。

### 4 个品种

| 品种 | code | 单位 | 参数项 |
| --- | --- | --- | --- |
| 电能 | `elec` | kWh | 46 项 |
| 水表 | `water` | m³ | 3 项 |
| 燃气 | `gas` | m³ | 3 项 |
| 蒸汽 | `steam` | t | 3 项 |

### 电能 46 项（最常用的 20 项）

| 键名 | 含义 | 单位 | 聚合 |
| --- | --- | --- | --- |
| `energy` | 本小时用电量（**增量**） | kWh | SUM |
| `energy_reading` | 正向有功总电度（**累积**） | kWh | MAX |
| `energy_day` | 当日累计 | kWh | MAX |
| `energy_peak` / `flat` / `valley` / `deep` / `tip` | 分时电量 | kWh | SUM |
| `power_total` / `power_a` / `_b` / `_c` | 有功功率 | kW | AVG |
| `voltage_a` / `_b` / `_c` | 相电压 | V | AVG |
| `current_a` / `_b` / `_c` | 相电流 | A | AVG |
| `power_factor_total` | 总功率因数 | — | AVG |
| `reactive_power_total` | 总无功功率 | kVar | AVG |
| `frequency` | 频率 | Hz | AVG |
| `demand_max` | 最大需量 | kW | MAX |
| `load_rate` | 负载率 | % | AVG |
| `voltage_unbalance` | 电压不平衡度 | % | AVG |

完整 46 项在平台里看：租户登录 → 能源参数字典 → 电能。

### 水 / 燃气 / 蒸汽（各 3 项）

| 键名 | 含义 | 聚合 |
| --- | --- | --- |
| `energy` | 本小时用量（增量） | SUM |
| `power` | 瞬时流量 | AVG |
| `energy_reading` | 累积表底 | MAX |

### ⚠ 三条铁律（现场接入 90% 的错误来源）

```
energy          本小时用了多少    1.20  1.35  0.98     ← 增量，不是表底
energy_reading  表上显示的总数    33705.42  33706.77  ← 只增不减
相邻两点之差必须相等：energy_reading[n] − energy_reading[n−1] == energy[n]
```

写成「energy = 表底」→ 月报表算出几十万度。

## 四、设备档案（7 个）

| 档案名 | 用途 | 认作表计 |
| --- | --- | --- |
| 单相电能表 | 1P2W，照明/插座回路 | ✓ |
| 电能表 | 3P4W，车间动力 | ✓ |
| 水表 | — | ✓ |
| 燃气表 | — | ✓ |
| 蒸汽表 | — | ✓ |
| 温湿度变送器 | 非计量 | ✗ |
| 网关 | RTU 网关本体 | ✗ |

**建档时必填 `isMeter`**：只有 `isMeter=true` 的档案才会被抄表、参数报表、
分项统计识别。建错了表现为「设备在，报表空」。

### 档案上预装的规则（建租户时自动）

两条电表档案上各挂一份规则，同档案的设备**开箱即带**，客户不用逐台配。

| 档案 | 类型 | 名称 | 判据 | 级别 |
| --- | --- | --- | --- | --- |
| 单相 / 三相 | 告警 | 电压越限 | `<198 V` 或 `>235 V`（GB/T 12325） | MAJOR |
| 单相 / 三相 | 告警 | 功率因数偏低 | `<0.90`（力率考核） | MINOR |
| 三相 | 告警 | 电压不平衡度超限 | `>2%`（GB/T 15543） | WARNING |
| 单相 / 三相 | 派生 | 负荷率 | `power_total / apparent_power_total × 100` | — |
| 单相 / 三相 | 派生 | 碳排放 | `energy × 0.5703 kgCO₂/kWh` | — |

合计 9 条（单相 4 + 三相 5）。阈值取在国标范围内，演示数据不会触发；
某台表真的越限时告警立刻出现，链路是通的。

**存在哪里**：`calculated_field` 表，`entity_id` 指向 `device_profile.id`。
在界面上看：租户 → 设备档案 → 选「单相电能表」→ 计算字段。

**想改阈值**：直接改档案上的规则，所有使用该档案的设备同时生效；
想给某台设备单独一套，再在那台设备上建一份覆盖。

## 五、分时时段方案（4 套）

没这套配置，峰谷报表**不报错但全算「平」** —— 页面有数，数也对，就是分不开。

| 方案名 | season | dayType |
| --- | --- | --- |
| 春秋季工作日 | `spring_autumn` | `weekday` |
| 夏季工作日 | `summer` | `weekday` |
| 冬季工作日 | `winter` | `weekday` |
| 春秋季周末 | `spring_autumn` | `weekend` |

每套含 `blocks`：`[{type, start, end}]`，档位 `tip/peak/flat/valley/deep`。

**时段必须首尾相接、无空洞**（`00:00` 到 `24:00` 全覆盖）。有空洞的小时会被归「平」。


**为什么两个场站**：单相表画不出分相电压/电流（电能质量页会空）；
只有三相表，现场大量单相回路又对不上。

**为什么电表要三级**：只有总表没有分表，分项分析和总分差全是空的；
只有分表没有总表，算不出线损和未装表率。

**设备名都带场站前缀**（`单相园-` / `三相园-`）：设备名在租户内唯一，
两个场站都会有一张「1#进线总表」，不加前缀第二张表会撞唯一索引，
整个演示包在这里中断。

**数据自洽**（每台表每个点都成立）：

```
I_φ = P_φ×1000/(U_φ×cosφ_φ)
S_φ = P_φ/cosφ_φ
Q_φ = √(S_φ²−P_φ²)
P_total = P_a + P_b + P_c          （最后一相用减法兜底）
cosφ_total = P_total / S_total     （不是简单平均）
energy_reading[n] = base + Σenergy[0..n]
Σ(尖峰平谷深谷) = energy
上级表 = 下级之和 × (1+未装表率) × (1+线损率)
```

### 两条硬限制

**1. 最多两层。** 侧边栏的 `menu-toggle` 把每个子项一律交给 `menu-link` 渲染，
而 `menu-link` 没有展开能力 —— 第三层点不动或跳到 undefined 路径。

**2. 客户菜单的绑定靠 `customer.customMenuId`，不是菜单的 `customer_id`。**

```
custom_menu.customer_id  →  恒为 NULL_UUID（NOT NULL 约束）
customer.custom_menu_id  →  指向具体菜单 id
```

客户登录时 `findCustomerHierarchyCustomMenu` 的查找顺序：

1. 按 `customer_id` 找默认客户菜单 → 命不中（是 NULL_UUID）
2. 读 `customer.customMenuId` 按 id 找 → **这一步对上才行**
3. 都没有 → 退回 TB 原生菜单

只建菜单不写 `customMenuId`，客户永远看到默认菜单。

## 六之三、垃圾数据已剔除

初始化模板里曾有两块没用的看板，已删除。**新部署不会再出现**：

| 删掉的模板 | 曾叫什么 | 为什么删 |
| --- | --- | --- |
| `verify_sankey.json` | 验证·能源流向 | 与 `sankey_flow.json`（能源流向）部件完全相同，是开发时的测试副本 |
| `bill_template.json` | 我的账单模板 | 只有 1 个 `billing_list` 部件，是 `my_bills.json`（4 个部件）的残缺子集 |

现存 **20 个**看板模板。判断标准：

- 与别的看板部件完全相同 → 副本，删
- 部件数明显少于同类看板、又没有独有功能 → 残缺版本，删
- 只有租户用得上（租户配给客户的）→ 保留，但不进客户菜单

**部件 FQN 前缀也修过**：模板里曾写 `tenant.energy_management.*`，
但部件实际建在系统租户（NULL_UUID）下，必须用 `system.` 前缀。
前缀错了前端会报「加载部件配置时出现问题。关联的 部件类型可能已被移除。」
现在 34 种部件类型全部用 `system.` 前缀，逐个实测都能加载。

## 八、用真数据替换演示数据

演示数据的作用是「让你立刻看到所有功能」。正式上线前应该：

1. **一键清掉演示实体**：客户 → 设备运维 → 平台自检 → 「清除演示数据」
   （只删 `demo=true` 的实体；也可用 `DELETE /api/energy/demo-data`，见「一之四」）
2. **建真实场站**：客户登录 → 组织与场站 → 新建
3. **建分项**：场站 → 用能结构 → 加分项
4. **建设备**：设备管理 → 新增，选对档案、挂对分项、标 `meterLevel`
5. **配 RTU**：拿到每台表的 Access Token，配到网关，见[④ 设备接入](/admin/device-access)
6. **等数据**：实时数据进来后，报表自动出数

**不想手工建**：客户填两张 CSV（场站、设备），用导入脚本：

```bash
bash scripts/05-import-customer-data.py --dir ./客户数据
```

模板在 `templates/` 下：`场站.csv`、`设备.csv`、`点位.csv`。
