### 还有一类「不在这张表里」的初始化：自建表

上面 17 项都是**数据**（实体、属性、遥测、菜单）。还有一类是**表结构本身** ——
抄表、手工填报、账单用的 5 张表不属于 ThingsBoard，是平台自己建的：

| 表 | 用途 | 谁建 | 什么时候 |
| --- | --- | --- | --- |
| `meter_reading_batch` | 抄表批次 | `EnergySchemaInstaller` | **服务启动时**自动，幂等 |
| `meter_reading_record` | 抄表明细（按月分区） | 同上 | 同上 |
| `billing` / `billing_detail` | 用能账单与明细 | 同上 | 同上 |
| `tb_sync_log` | 同步日志 | 同上 | 同上 |

**不需要手工建**。它挂在 `ApplicationReadyEvent` 上，两个阶段都会触发：

```
docker-01-install.sh（建库）→ 表在这里就建好了   ← 全新安装走这条
energy-server 启动         → 表已在，跳过（幂等）
```

判断方法（**先查表在不在，别只看 server 日志**）：

```bash
# 1. 表在不在（唯一判据）
docker compose exec -T postgres psql -U postgres -d thingsboard -tAc "
SELECT t, CASE WHEN to_regclass('public.'||t) IS NULL THEN '缺失' ELSE 'OK' END
FROM unnest(ARRAY['meter_reading_batch','meter_reading_record',
                  'billing','billing_detail','tb_sync_log']) AS t;"

# 2. 建表日志在哪
grep energy-schema /tmp/energy-install.log    # install 阶段（全新安装看这里）
docker compose logs energy-server | grep energy-schema   # server 阶段（表缺时才打）
```

⚠️ `docker logs energy-server` 里**没有** `energy-schema` 不代表没建 ——
全新安装时是在 install 阶段建的，server 起来只会看到表已存在（走 DEBUG，不打 INFO）。

**为什么单独说这件事**：这 4 张表的 DDL 早就写在
`nenghaobao/energy-config/sql/`，但当初只有一个手工迁移脚本把它们建在
**开发库**上，从未纳入自动流程。于是开发机一切正常、新装出来 0 张表，
抄表与手工填报 7 个接口全 500（实测 2026-10-22）。
现在纳入启动自检，`08-verify-release.sh` 里也有 3 条断言盯着。

> 如果你在排查「某个页面报 500 / 提示表不存在」，先跑
> [⑤ 常见问题 → 14.18 自建表健康检查](/admin/troubleshoot#_14-18-自建表健康检查-部署后必查一次)。

## 一之二、这份数据该建在哪一级（一条判断法）

初始化最容易出错的地方不是「建没建」，而是「建在哪一级」。建错层级的症状
往往**不报错**：页面照常打开，只是数据对不上、换个客户就没了。

三层，只问一句话：

> **「这个东西会不会被第二个客户 / 第二台设备用到？」**

| 层级 | 判断 | 典型对象 | 谁继承 |
| --- | --- | --- | --- |
| 系统级 | 平台自带，与租户无关 | 部件库、语言包、系统规则链 | 全部租户 |
| **租户级（模板）** | 会复用，改一次应全部生效 | 参数字典、资产档案、设备档案、厂商型号、分时方案、费率模板（仅示例价）、**挂在设备档案上的告警规则与计算字段** | 该租户下全部客户 |
| **客户级（实例）** | 有明确归属：某客户、某场站、某台设备 | 场站、分项、区域、空间位置、用能性质、设备、遥测、看板副本、客户菜单 | 只有该客户 |

**会 → 租户级，建一次；不会 / 有归属 → 客户级，跟着客户建。**

### 能源主数据的层级对照（2026-10 定稿）

| 主数据 | 层级 | 为什么 |
| --- | --- | --- |
| 能源参数字典（品种 → 标准指标 key） | **租户级** | 设备上报的键名必须全租户一致，否则报表部件认不出，表现为「有数据、图表空」 |
| 分时时段方案 `tou_scheme` | **租户级** | 电价政策按省统一，跨客户共用 |
| 费率模板 `rate_template` | **租户级** | 只作「填入示例价」的参考；**价格的真实来源是客户自填的 `customer.additionalInfo.energyRates`** |
| 四棵分类树（分项 / 区域 / 空间位置 / 用能性质） | **客户级** | 每个客户怎么组织自己的设备完全不同，不能共用 |
| 场站、设备、遥测、看板副本、客户菜单 | **客户级** | 有明确归属 |

> **客户级 / 租户级的判断写法有个坑**：TB 里租户级实体的 `customerId`
> 是 **NULL_UUID**（`13814000-1dd2-11b2-8080-808080808080`），**不是 `null`**。
> 判断必须写 `customerId == null || customerId.isNullUid()`；
> 只写 `== null` 会永远不成立，把所有租户级主数据全部过滤掉 ——
> 实测后果是「品种指标」页 0 个品种、场站费率页 0 模板 0 方案，且**不报错**。

### 四个踩过的坑（照着反例记）

- **告警规则建在设备上** → 换一台表就没了，第 21 台表没有人管。
  正确：建在**设备档案**（`DEVICE_PROFILE`）上，同档案设备自动继承。
- **资产档案等到用到才建** → 漏建时 `assetProfileId` 写 null 也不报错，
  页面照常渲染，但按档案筛选、模板、统计全空。
  正确：建租户时**一次建全 14 个**，之后所有路径只查不建。
- **分类树根建在每个客户下** → 20 个客户 20 套根，跨客户无法横向汇总。
  **定稿**：4 棵根**明确建在客户级**（每个客户一套）—— 分项 / 区域 / 空间位置 /
  用能性质本来就是「这个客户怎么组织自己的设备」，共用反而是错的。
  需要跨客户汇总的维度请用租户级的**品种**口径，不要指望分类树。
  读取侧已加守卫：客户没有自己的根时**返回空**，不再回退到别的客户的树
  （早先的 `return all.get(0)` 会让容器建到别人树下，客户自己还看不见）。
- **计算字段建在具体设备上** → 新建的表没有派生指标。
  正确：`calculated_field` 的 `entity_id` 写 **DeviceProfileId**，这是 TB 里
  唯一能让「模板 → 实例」自动生效的形态。

### 一个例外：重名

资产名、设备名在**租户内**唯一（唯一键是 `(tenant_id, name)`，不是客户内），
所以两个场站各有一台「1#进线总表」会撞键。
解决办法是**展示用 `label`、唯一用 `name`**：`name` 加场站前缀（如 `单相园-1#进线总表`），
`label` 留业务原名。前端渲染一律取 `label || name`。
这属于命名约定，不改变「场站/设备是客户级实例」的定位。

## 一之三、装完第一件事：打开「平台自检」

**路径**：租户管理员 → 运营配置 → 平台自检；客户用户 → 设备运维 → 平台自检。

这一页把上一张清单里的每一项**逐条数一遍**，给出四类状态：

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| 正常 | 数量达标 | 不用管 |
| 不完整 | 有，但数量不足 | 功能能跑，报表会缺角 —— 按提示补 |
| 缺失 | 完全没有 | 对应功能不可用 —— 按提示补 |
| 可选 | 暂时不需要（如演示数据已清） | 不用管 |

每一条都带三样东西：**缺了会怎样**、**怎么补**、**看手册哪一页**。
顶部横幅一眼看出整体健康度：全绿才算初始化完整。

> 为什么值得先看这一页：初始化缺项**不会报错**。
> 页面照常打开、按钮照常能点，只是某些报表空白、某些统计为 0。
> 不看自检，往往要等到客户提问才发现缺东西。

自检项与文档的对应关系：

| 自检项 | 缺失后果 | 手册 |

| 租户菜单（能源导航） | 租户看不到能源入口，只剩 TB 原生菜单 | 本页「六之二」 |

### 建一个客户时，平台自动做这四件事

以前只有「一键修复初始化」会做其中三件，全新库装完自己修不了 ——
现在 `onCreateCustomer` 一次做全（每步独立 try-catch，失败不拖垮客户创建）：

| 顺序 | 动作 | 少了会怎样 |
| --- | --- | --- |
| ① | 电表 Key 标准化节点（**租户级**规则链） | RTU 原始代号落库，报表读不到数 |
| ② | 4 个维度根（用电分项 / 用能区域 / 用能性质 / 空间位置） | 用能结构页空白 |
| ③ | 演示数据包（2 场站 / 21 设备 / 逐小时遥测） | 装完看不到效果 |
| ④ | 组织 + **演示费率** | 出账全部「未配置电价」跳过 |

④ 必须在 ③ 之后 —— 组织要把演示场站挂到自己名下。

> **演示费率是示例价，不是合同价。** 数值与「费率模板」一致
> （电 0.72 平档 / 水 4.50 / 气 3.60 / 汽 260，基本电费按 50 kVA × 30 元）。
> 上线前必须按当地目录电价改：组织 → 能源费率。
> 已有任何费率时平台**不会**覆盖，客户改过的价一个字都不动。

## 一之四、演示数据：生成、清除、换成自己的

新客户建出来时带一套演示数据（2 个场站、21 台设备、14 天遥测），
目的是**装完就能看到完整效果**，不用等 RTU 接入。

但它只是样板。接入真实设备后的正确做法是：

1. 先按[设备接入](/admin/device-access)把 RTU 接上，验一条数据能上报
2. 打开客户 → 设备运维 → **平台自检** → 「清除演示数据」
3. 按自己的业务建场站 → 分项 → 设备 → 拓扑

**清除只删带 `demo` 标记的实体**，你自己建的东西一个都不动。
清错了也没关系：同一页有「生成演示数据」，可随时重建（幂等，已存在则跳过）。

| 操作 | 页面 | 命令行 |
| --- | --- | --- |
| 看数量 | 平台自检 → 演示数据 | `GET /api/energy/demo-data` |
| 生成 | 点「生成演示数据」 | `POST /api/energy/demo-data` |
| 清除 | 点「清除演示数据」 | `DELETE /api/energy/demo-data` |

## 一之五、两个典型故障与修复

### 故障一：看板里图表全空，控制台刷 `404`

**现象**：客户登录后，能耗概览/历史能耗等看板里部分部件一直转圈或空白。
浏览器 Network 里能看到：

```
GET /api/relations?fromId=00000000-0000-0000-0000-0000000005a1&fromType=ASSET...  → 404
GET /api/asset/00000000-0000-0000-0000-00000000d101                              → 404
```

**原因**：看板模板里的实体引用是**占位符**（`00000000-…-00000000xxxx`），
复制给客户时要**按引用性质分别处理**：

| 引用的是什么 | 该怎么做 |
| --- | --- |
| 场站、4 个维度根、分项根（**客户级**） | 替换成该客户真实 id |
| 能源参数字典、电能品种（**租户级**） | **保留占位符** |

旧版本的替换函数有个判断写错，**从没真正执行过** ——
连客户级的场站/维度根也没换，前端拿占位符去查，必然 404。

**怎么判断是不是这个**（占位符**用对了地方**，所以不能一刀切查计数）：

```bash
# 客户看板里应该有「场站 / 维度根」的真实 id
docker compose exec -T postgres psql -U postgres -d thingsboard -tAc \
  "SELECT count(*) FROM dashboard
   WHERE customer_id IS NOT NULL
     AND configuration LIKE '%00000000-0000-0000-0000-0000000005a1%';"
# 期望 0（05a1 = 场站的占位符，客户副本里不该还有它）
```

**修复**：点**平台自检 → 一键修复初始化**。它会就地重写客户看板的
`configuration`，把该替换的占位符换成真实实体 id —— **不删看板、不重建客户、
不动你的场站设备和遥测**。耗时约 5–10 秒。

```bash
curl -s --noproxy '*' -X POST -H "X-Authorization: Bearer $TOK" \
  http://127.0.0.1:8090/api/energy/repair-init
```

返回里 `dashboardsFixed` 是本次修好的看板数。修完再查一次，计数应为 0：

```bash
docker compose exec -T postgres psql -U postgres -d thingsboard -tAc \
  "WITH ta AS (
   SELECT id::text AS aid FROM asset
   WHERE customer_id = '13814000-1dd2-11b2-8080-808080808080')
 SELECT count(*) FROM dashboard d, ta
 WHERE d.customer_id IS NOT NULL AND d.configuration LIKE '%'||ta.aid||'%';"
```

**期望 0**。大于 0 说明客户看板里存了**租户级资产**的真实 id ——
客户无权读，会一直刷 403（详见故障排查「现象 I」）。

> **哪些 id 该留占位符、哪些该替换**（这是最容易搞错的地方）：
>
> | 引用 | 该怎么做 | 原因 |
> | --- | --- | --- |
> | 场站、4 个维度根、分项根 | **替换**成客户真实 id | 客户级实体，客户有权读 |
> | 能源参数字典、电能品种 | **保留占位符** | 租户级主数据，客户读会 403 |
>
> 租户名下那 20 个看板是**模板**，里面全是占位符，设计如此；
> 租户直接点开模板看板会看到空图，那是正常的 —— 看效果请用客户账号。

### 故障二：租户左侧菜单只剩几项，TB 原生菜单像被删了

**现象**：租户登录后左侧只有 首页 / 能源管理 / 告警中心 / 模型训练平台 等 6 项左右，
IoT Hub、实体、客户与用户、资源、安全这些全都不见了。

**原因**：自定义菜单只写「引用某个默认项」（如 `{id: "iot_hub"}`），
不重复写它的子菜单。而 `iot_hub` 这类顶层项在前端 `menuSectionMap` 里
**只声明了容器、没有 pages**（子菜单一直由 `defaultUserMenuMap` 提供）。
旧版前端遇到「toggle 型但没有 pages」就整项丢弃 —— 于是只剩 link 型的几项。

**注意**：数据没坏，菜单配置在库里是完整的 11 项。
换上新前端就恢复，**不需要重装、不需要重跑初始化**。

**验证配置本身没丢**：

```bash
TOK=$(curl -s --noproxy '*' -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"tenant@126.com","password":"12345678"}' \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")
```

## 三、能源参数字典（字段定义）

这是**全平台的数据字典** —— 设备上报的键名必须与它一致，否则存不进去。

> **不用背这张表。** 登录租户 → **运营配置 → 品种指标**，
> 选品种就能看到它的全部设备类型和标准 key，点 key 直接复制。
> 下面几节是给写脚本/做对接的人查的，现场配 RTU 用那个页面更快。

### 4 个品种

| 品种 | code | 单位 | 参数项 |
| --- | --- | --- | --- |
| 电能 | `elec` | kWh | 26 项一级指标（48 个二级 key） |
| 水表 | `water` | m³ | 3 项 |
| 燃气 | `gas` | m³ | 3 项 |

### 电能 26 项（最常用的 20 项）

指标是**两级**的：一级是报表里选的名字，二级是设备实际要上报的 key。

| 一级指标 | 二级 key | 单位 | 聚合 |
| --- | --- | --- | --- |
| 用电量 | `energy`（本小时，**增量**） | kWh | SUM |
| 正向有功总电度 | `energy_reading`（**累积表底**） | kWh | MAX |
| 当日正向有功总电度 | `energy_day` | kWh | MAX |
| 正向有功尖/峰/平/谷电度 | `energy_tip` / `energy_peak` / `energy_flat` / `energy_valley` | kWh | MAX |
| 相电压 | `voltage_a` / `_b` / `_c` / **`voltage_avg`** | V | AVG |
| 相电流 | `current_a` / `_b` / `_c` / **`current_avg`** | A | AVG |
| 有功功率 | `power_a` / `_b` / `_c` / `power_total` | kW | AVG |
| 无功功率 | `reactive_power_a` / `_b` / `_c` / `reactive_power_total` | kVar | AVG |
| 视在功率 | `apparent_power_a` / `_b` / `_c` / `apparent_power_total` | kVA | AVG |
| 功率因数 | `power_factor_a` / `_b` / `_c` / `power_factor_total` | — | AVG |
| 频率 | `frequency` | Hz | AVG |
| 最大需量 | `demand_max` | kW | MAX |
| 负载率 | `load_rate` | % | AVG |
| 电压不平衡率 | `voltage_unbalance` | % | AVG |
| 电流谐波畸变率 | `current_thd_a` / `_b` / `_c` | — | AVG |
| 电压谐波畸变率 | `voltage_thd_a` / `_b` / `_c` | — | AVG |

完整 26 项在平台里看：租户 → 运营配置 → **品种指标** → 电能。

> **为什么电压/电流的汇总项叫 `_avg` 不叫 `_total`**：
> 功率可以相加（`power_total` = A+B+C），电压和电流不能相加，
> 三相的合理汇总只有平均值。名字跟着语义走，避免现场配错。

### 单相表 vs 三相表：指标不一样

这是接入时最容易搞错的一处。**三相表的指标包含单相表的全部指标**，反过来不成立。

| 指标 | 单相表（1P2W） | 三相表（3P4W） |
| --- | --- | --- |
| A 相电压/电流/功率/功率因数 | ✓ | ✓ |
| B 相、C 相各项 | **✗ 不存在** | ✓ |
| `*_total` / `*_avg` 汇总项 | ✓ | ✓ |
| 电压不平衡率 | ✓（恒为 0） | ✓（有意义） |
| 频率 / 需量 / 负载率 / 电度类 | ✓ | ✓ |

判据只有一条：**键名以 `_b` / `_c` 结尾的，单相表不会有**。

在「品种指标」页面里选一下「单相电能表」，不适用的 key 会自动灰显并标注
「单相不适用」—— 现场照着配就不会多配不存在的相别。

> 单相表配了 B/C 相会怎样：那几项永远是空的。报表能出，图表也能画，
> 只是那几条线一直缺 —— 不报错，但会让人以为设备坏了。

### 水 / 燃气 / 蒸汽（各 3 项）

| 键名 | 含义 | 聚合 |
| --- | --- | --- |
| `energy` | 本小时用量（增量） | SUM |
| `power` | 瞬时流量 | AVG |
| `energy_reading` | 累积表底 | MAX |

### 「品种指标」页面

**路径**：租户 → 运营配置 → **品种指标**。

三个区块，从上到下：

1. **品种切换**：电能 26 项 / 水表 3 项 / 燃气 3 项 / 蒸汽 3 项
2. **适用设备类型**：该品种下有哪些设备档案（单相电能表 1P2W、电能表 3P4W…），
   带接线方式与「计量 / 非计量」标记。**点一个类型**，下方指标立即标出它上报不了的项
3. **标准参数指标**：两级表格
   - 一级行：指标名 + `适用数/总数`（如相电压在单相表下显示 `2/4`）+ 单位 + 聚合方式
   - 二级行：每相 / 汇总项各一行，**key 可点击复制**；不适用的灰显 + 删除线 + 标「单相不适用」

选「单相电能表」时页面顶部会出现黄色提示，说明 B／C 相不会上报 ——
这是本页最容易误解的地方，所以做成显式提示而不是让人自己推断。

**聚合方式这一列必须看懂**，它是「上级表 = 下级表之和」这类校验的基础：

| 值 | 含义 | 典型指标 |
| --- | --- | --- |
| `SUM` | 区间累加 | `energy`（本小时用电量） |
| `MAX` | 取末值（表底） | `energy_reading`（正向有功总电度） |
| `AVG` | 区间平均 | `power_total`（有功功率） |

写错聚合方式不会报错，但报表会算错：把表底当累加，一天的电量会变成
「最后一块表的读数」；把累加当表底，曲线会一路冲高。

**未归品种的档案**（网关、温湿度变送器）会单独列在页脚 ——
它们不参与分品种统计，属正常。

#### 能改什么、不能改什么

品种摘要行右侧有「编辑展示字段」，可改：全名、计量单位、图标、颜色、排序、备注。

**不能改**：品种编码（`code`）与指标 key。

为什么把话说死：这两样是**契约**，不是标签。

- `code` 是下游部件识别品种的依据（`elec` 改了，所有按品种取数的部件都认不出）；
- 指标 key 是设备上报的字段名（`voltage_a` 改成 `ua`，设备照旧报 `voltage_a`，
  数据能存进去，但所有报表都不认它 —— 现象是「设备有数据、图表全空」，**且不报错**）。

所以这一页给的是「改标签不改契约」的能力。要加指标、删指标，改
`energy_library.json` 后重建租户，不要指望在页面上点。

改完立刻生效（写的是租户级字典的属性），不用重启。
权限：只有租户管理员能改，客户账号调用会 403。

### ⚠ 三条铁律（现场接入 90% 的错误来源）

```
energy          本小时用了多少    1.20  1.35  0.98     ← 增量，不是表底
energy_reading  表上显示的总数    33705.42  33706.77  ← 只增不减
相邻两点之差必须相等：energy_reading[n] − energy_reading[n−1] == energy[n]
```

写成「energy = 表底」→ 月报表算出几十万度。

### 字典升级：为什么老租户要「一键修复」

资源文件 `energy_library.json` 会随版本加指标，但**平台读的是库里的 `paramDict` 属性**，
不是资源文件。所以：

- 新建租户 → 直接拿到最新指标
- 已有租户 → 早退分支会跳过建字典，资源文件里新增的指标**永远拿不到**

解决办法是初始化时跑一次 `upgradeDictionaryParams`：按「品种名 + 一级指标名 + 缺失 key」
精确补，只补缺的，不改名、不重排、不动客户自己加的条目。

**当前这一版补了什么**：

| 一级指标 | 补的子项 | 为什么 |
| --- | --- | --- |
| 相电压 | `voltage_avg`（平均相电压） | 原来只有 A/B/C 三相，缺汇总项 |
| 相电流 | `current_avg`（平均相电流） | 同上 |

**为什么叫 `_avg` 不叫 `_total`**：电压、电流不能相加。功率能相加所以是 `power_total`，
电压电流的合理汇总只有平均值。名字跟语义走，避免现场配错。

字典的 `paramDict.version` 从 3 升到 4，只有真补了子项才写库（不会每次初始化都增一条时报）。

**怎么触发**：平台自检 → 一键修复初始化。日志里会打
`[energy] 字典品种「电能」已补齐新指标`。

### 档案上预装的规则（建租户时自动）

两条电表档案上各挂一份规则，同档案的设备**开箱即带**，客户不用逐台配。

| 档案 | 类型 | 名称 | 判据 | 级别 |
| --- | --- | --- | --- | --- |
| 单相 / 三相 | 告警 | 电压越限 | `<198 V` 或 `>235 V`（GB/T 12325） | MAJOR |
| 单相 / 三相 | 告警 | 功率因数偏低 | `<0.90`（力率考核） | MINOR |
| 三相 | 告警 | 电压不平衡度超限 | `>2%`（GB/T 15543） | WARNING |
| 单相 / 三相 | 告警 | 闲时能耗超标 | `idle_exceed == 1` | MINOR |
| 单相 / 三相 | 派生 | 负荷率 | `power_total / apparent_power_total × 100` | — |
| 单相 / 三相 | 派生 | 碳排放 | `energy × 0.5703 kgCO₂/kWh` | — |

合计 11 条（单相 5 + 三相 6）。前三条阈值取在国标范围内，演示数据不会触发；
某台表真的越限时告警立刻出现，链路是通的。

### 「闲时能耗超标」为什么只看一个 0/1

判定「现在算不算闲时、有没有超标」需要场站班次表和两个阈值，
只有服务端的闲时能耗模块拿得到。它每天算完写一个结果到设备上：

```
idle_exceed = 1   超标
idle_exceed = 0   正常
```

计算字段只做翻译：`1` → 创建告警，`0` → 清除告警。

**所以阈值只有一处**：「组织与场站 → 场站 → **空闲时段** → 基线与阈值」里的
「闲时待机功率阈值」「闲时能耗占比阈值」。改那里，告警自动跟着变。
设备档案上**不再**存第二份阈值 —— 那正是我们删掉的旧做法
（两份配置只有一份生效，页面显示保存成功但永远不告警）。

**验证链路通不通**（一条命令）：

```bash
# 手动写一个"超标"结果，10 秒后应出现告警
curl -s --noproxy '*' -X POST \
  -H "X-Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{"idle_exceed":1}' \
  "http://127.0.0.1:8090/api/plugins/telemetry/DEVICE/$DEV/timeseries/SERVER_SCOPE"

# 写 0 应清除
curl -s --noproxy '*' -X POST \
  -H "X-Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{"idle_exceed":0}' \
  "http://127.0.0.1:8090/api/plugins/telemetry/DEVICE/$DEV/timeseries/SERVER_SCOPE"
```

实测结果：`1` → 告警中心出现「闲时能耗超标」MINOR / 未确认；
`0` → 同一条告警转为「已清除 / 未确认」。这条链路是验过的。

**存在哪里**：`calculated_field` 表，`entity_id` 指向 `device_profile.id`。
在界面上看：租户 → 设备档案 → 选「单相电能表」→ 计算字段。

**一个必须知道的技术细节**：TB 的计算字段参数（`TS_LATEST`）**只从本次上报的
那批遥测里取值，不会去库里查最新点**。所以 `idle_exceed` 必须以「遥测写入」的
方式推过去，直接把值写进 `ts_kv` 表是**不会触发告警**的 ——
症状是规则一直报 `Required arguments are missing: exceed`，一条告警都不出。

闲时模块的重算就是按这个要求实现的：历史天数的结果直写（不触发，避免刷屏），
**最新一天额外经遥测订阅服务推一次**，顺带触发告警评估。

**想改阈值**：直接改档案上的规则，所有使用该档案的设备同时生效；
想给某台设备单独一套，再在那台设备上建一份覆盖。

**演示数据自带一套**：新建客户时会自动给两个场站写 `idleConfig`
（单相园 3.0 kW、三相园 150 kW，工作时段 08:00–17:00）并跑一次真实重算。
所以客户建完，「空闲时段」页有数据、「告警中心」里能看到「闲时能耗超标」，
不用手工配。

## 五之二、电表 Key 标准化节点

现场 RTU 按**厂家手册**发数据，键名是 `U` / `I` / `P` / `Ep` 这种原始代号；
平台所有报表、告警、账单只认一套标准名：

```
RTU 原始代号          平台标准名
U              →     voltage_a
I              →     current_a
P              →     power_total
Q              →     reactive_power_total
S              →     apparent_power_total
PF             →     power_factor_total
Freq           →     frequency
Ep             →     energy_reading
```

翻译发生在**根规则链**里，不在设备侧 —— 换厂家不用重烧固件：

```
设备上报
   │
   ▼
[Message Type Switch] --Post telemetry--> [电表Key标准化] --Success--> [Save Timeseries]
```

### 为什么必须由平台装好

节点缺了**不报错**：

- 上报接口照样返回 `200`
- `ts_kv` 里存的是 `U` / `I` / `P`，不是 `voltage_a`
- 报表按标准名取数 → **全空**

所以它被纳入「平台自检」和「一键修复初始化」：

```bash
curl --noproxy '*' -s -X POST \
  -H "X-Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8090/api/energy/repair-init | jq '.meterKeyTransformFixed'
```

第一次装会返回 `true`；已经装好时返回 `false`（幂等）。
自检里对应项是 `tenant.meter-key-transform`。

### 自己改脚本时的两条硬约束

规则节点的 JS 由平台包装后执行，**入参已经是对象、返回值会被再序列化一次**：

```js
function wrapper(msgStr, metadataStr, msgType) {
    var msg = JSON.parse(msgStr);        // 传入脚本时 msg 已经是对象
    var metadata = JSON.parse(metadataStr);
    return JSON.stringify(ruleNodeFunc(msg, metadata, msgType));  // 返回值会被 stringify
}
```

由此：

- **不要**在脚本里再 `JSON.parse(msg)` / `JSON.parse(metadata)`
  → 会抛异常，脚本走 `catch` 后原样返回，表现为「节点配了但数据没转换」
- **不要**在脚本里 `JSON.stringify(...)` 返回值
  → 会得到带引号的字符串，`Save Timeseries` 报 `Can't parse value`

正确写法（节选）：

```js
var out = {};
out["voltage_a"] = msg["U"];
return {msg: out, metadata: metadata, msgType: msgType};
```

### 验证

```bash
# 1. 节点在不在（应为 1）
docker exec energy-postgres psql -U postgres -d thingsboard -At -c \
  "select count(*) from rule_node where name='电表Key标准化';"

# 2. 上报一组原始代号，6 秒后看标准名是否更新
#    原始键 U 的时间戳应停在本次上报之前
```

**只转换表里列出的代号**，其它 key 原样保留 —— 已经上报标准名的设备重复经过本节点也不会被改坏。

**数据自洽**（每台表每个点都成立）：

```
I_φ = P_φ×1000/(U_φ×cosφ_φ)
S_φ = P_φ/cosφ_φ
Q_φ = √(S_φ²−P_φ²)
P_total = P_a + P_b + P_c          （最后一相用减法兜底）
cosφ_total = P_total / S_total     （不是简单平均）
energy_reading[n] = base + Σenergy[0..n]
Σ(尖峰平谷深谷) = energy
上级表 = 下级之和 × (1+未装表率) × (1+线损率)
```

| **场站** | **第一个场站**（不是「全部」） | 锁定后在树里只留下这个场站的分组 |
| **维度** | **全部维度** | 可切到单棵（用电分项 / 用能区域 / 用能性质 / 空间位置） |
| **搜索** | 空 | 按分类名过滤，自动展开命中路径 |

**为什么场站必须排在第一位、且默认落到第一个**：

一个客户下通常有多个场站，而**每个场站在四棵维度树里各有一个同名容器**
（都叫「演示园区」）。默认「全部场站」时，树里会同时出现 N 个同名容器，
用户根本分不清点的是哪个场站的分类。先锁场站，树里就只剩这一个场站的。

**为什么维度默认「全部」而不是第一棵**：

场站锁定之后，每个维度在这棵树里只剩**一个**容器，四棵并排不再混淆。
此时默认全选是有价值的 —— 用户能一眼看到「这个场站在分项/区域/性质/位置
各有什么」。改版前四棵树并排、且场站未锁，才是「看不清」的根源。

**左侧树只显示分类，不显示设备**（改版重点）：

- 树是「分类结构」的表达。设备混在里面会让同一个设备在四棵树里各出现一次，树又深又重复。
- 「这个分类下有哪些表」在**右侧抽屉**里看 —— 选中分类，右侧列出它子树下的全部设备。
- 每个分类名右侧有一个「N 表」徽标，告诉你这个分类（含子分类）挂了几台设备。
  没有徽标 = 空分类，点进去也不会有设备。

**设备怎么挂到分组上**（三条路径，任选）：

1. 选中分类 → 右侧抽屉顶部「**添加设备**」
2. 左侧树分类行的「**⋮**」菜单 → 添加设备
3. 分类下没有设备时，抽屉里的空态**直接带「添加设备」按钮** ——
   看到「还没有设备」的第一反应就是「那怎么加」，不用再回顶部找

**「添加设备」是购物车式的**（2026-10-22 改）：

弹窗分左右两栏，左边挑、右边看已选。

- **左栏**：设备清单 + 搜索 + 档案筛选（电能表 / 水表 / 燃气 …）。
- **「全选当前结果」**：一次把**筛选后可见**的设备加进已选。
  它只作用于当前搜索结果 —— 搜了什么就加什么，不会把没看到的也偷偷加进来。
- **右栏**：已选清单，每行带一个 `×` 可以随时摘掉挑错的。
- 底部按钮显示「绑定 N 台设备」，一眼知道这次要绑几台。

为什么改成两栏：原来是单列表 + 复选框，勾完就看不见了 ——
挑到第 8 台时已经记不清前 7 台是什么。

**怎么解绑**：设备行右侧的「**解除绑定**」按钮（图标是一段断开的链条）。

- 只断开「分类 ↔ 设备」的关系。**设备本体、接入令牌、历史遥测全部保留**，
  它仍然在「设备管理」页里，只是不再属于这个分类。
- 图标刻意不用「删除」样式：那个动作看起来像删设备，会让人不敢点。
- 也可以把设备拖到别的分类上（换分组），效果等同「解绑 + 绑定」。

**数据看哪**：抽屉里列的是这个分类**连同所有子分类**下的设备（递归），
标题旁的「含子分类」就是在说明这个口径。同一台设备只出现一次，
即使它在多级子分类下。要精确看某个子分类，点它自己。

**两条硬规则**（来自 TB 计算字段的聚合行为，违反会重复计算电量）：

- 设备只能挂在**叶子分类**下。有子分类的节点不能再挂设备 ——
  否则上级 = 子分类（已含该设备）+ 直属设备，算两遍。
  有子分类时「添加设备」按钮是灰的，悬停会说明原因。
- 同一设备在**同一棵维度树**里只能出现一次。跨维度重复不受影响
  （「电源组」和「电源区」是两棵独立的树）。已挂过的设备在弹窗里标「重复」。

**「新建子分类」弹窗里分类类型不可改**（2026-10-22 改）：

分类类型由父级决定 —— 在「用电分项」树下建子分类，它必然属于用电分项。
只显示、不可选。此前允许改，等于让用户在弹窗里把节点挪到另一棵树，
建完在原来的树下找不到，看起来像「建失败了」。

**父级分类路径用显示名**：形如「用电分项 / 三相场站 / 照明」。
括号里的技术名（`照明分项·三相园·星河工业园`）是租户内唯一约束的产物，
不出现在界面上。

**网关不参与分组**（2026-10-22 定）：

网关的角色是「代下级设备上报」的通信代理，本身不产生能耗。把它挂进分项，
上级汇总里会多出一行没有电量、也无法解释的节点。所以「添加设备」的候选**不含网关**，
弹窗底部会说明「已隐藏 N 台网关」。**普通设备与虚拟设备都要参与** ——
虚拟表往往正是分项电量的直接来源。

### 场站详情页的选项卡

点开任一「场站」节点，右侧有 7 个选项卡：

```
概览 / 设备管理 / 数据接入 / 场站配置 / 费率方案 / 空闲时段 / 用户管理
```

| 选项卡 | 配什么 | 效果 |
| --- | --- | --- |
| 概览 | 场站名称、地址、行业、变压器容量、负责人、能耗类型（可多选） | 保存即生效 |
| 设备管理 | 本场站挂了哪些设备 | 保存即生效 |
| 数据接入 | 每台设备的 MQTT / HTTP 接入令牌 | 保存即生效 |
| 场站配置 | 用能等级分档、能源供应周期 | **只保存，暂不参与计算**（见下） |
| 费率方案 | 本场站用哪套电价（两层来源，见下） | 保存即生效 |
| 空闲时段 | 班次表 + 默认工作时段 + 待机功率/闲时占比阈值 | 保存即生效 |
| 用户管理 | 谁能看这个场站 | 保存即生效 |

#### 场站配置：这两块暂时不算数

「用能等级」和「能源供应周期」是产品规划里的功能（分级考核 / 季节对比），
**当前版本只存不用** —— 全仓库只有这一页读写它们，后端不读、报表不算、看板不显示。
页面上有橙色提示标注这件事。

字段结构已经按最终形态定好，现在录入的内容不会白填：后续版本接入计算时直接生效。
不想现在配就留空，不影响任何现有功能。

#### 费率方案：两层来源 + 组织继承链

```
1. 本场站自定义     只影响这个场站，优先级最高
2. 继承费率         沿父链向上找最近一个配了费率的组织 ＞ 客户级兜底
```

**谁在哪配**（三个入口，各管一层）：

| 谁 | 入口 | 存哪 | 生效范围 |
| --- | --- | --- | --- |
| 客户 | 组织 → **能源费率** 选项卡 | 组织资产 `energyRates` | 本组织及下属场站（下级组织没配时继承） |
| 租户 | 客户列表 → 行图标 **能源建档** | 客户档案 `energyRates` | 该客户所有组织都没配时的兜底 |
| 客户/租户 | 场站 → **费率方案** | 场站属性 `siteCustomRates` | 仅该场站，优先级最高 |

**客户为什么在组织层维护**：客户登录后看不到「客户列表」（`GET /api/customers` 返回 403），
只能看到自己的资产。组织是他能操作的层级，场站再向下继承 ——
一个组织谈一次价，下属场站自动跟上。

**客户侧操作路径（照着念给客户听）**：

```
用客户账号登录
  → 左侧菜单「组织」（图标是楼宇）
  → 在左侧树里点中组织（如「总部·某某公司」）
  → 右侧出现两个选项卡：概览 / 能源费率
  → 点「能源费率」
  → 每个品种选计价方式、填单价；没把握先点「填入示例价」
  → 点「保存费率」
```

保存后**该组织下属所有场站立刻按新价结算**（场站没单独配过的话）。
要点：
- 计价方式的下拉只列这个品种支持的（蒸汽只有单一制，不是 bug）
- 阶梯计价点「加一档」，末档「到量」留空表示不封顶
- 填了价就算开通，某个品种全清空就算停用
- 场站要单独的价 → 场站详情 → **费率方案** → 自定义（优先级最高）

**没有「租户模板 → 客户引用」这一层了。**

早先是三层（租户模板 → 客户引用 → 场站覆盖），已删除，原因：
- 客户看着「继承客户默认」看不到继承的是哪份模板；
- 模板本身也没有消费方（当时 `energy_bill` 资产还没人生成；出账已在 2026-10 上线，见第十节）；
- 三层里只有中间层能被客户改，改完还看不见自己改的是什么。

现在的层级（越靠上优先级越高）：

```
场站自定义  siteCustomRates        只影响该场站
组织费率    组织资产 energyRates     下属场站继承（沿父链向上找最近一层配了的）
客户兜底    客户档案 energyRates     该客户所有组织都没配时用
```

**客户维护的是组织级**，不是客户级。原因：客户登录后看不到「客户列表」
（`GET /api/customers` 对客户账号返回 403），只能操作自己的资产 ——
组织是他能进的层级。租户才用「客户列表 → 能源建档」给客户打底。

三处结构完全一致（同一套字段），所以读取方不用关心值来自哪一级：

```json
{
  "elec":  { "rateType": "tou",  "prices": { "tip": 1.42, "peak": 1.18, "flat": 0.75,
                                             "valley": 0.36, "deep": 0.24 },
             "basicFee": { "mode": "capacity", "price": 32 },
             "effectiveDate": "2026-01-01" },
  "water": { "rateType": "tier", "tiers": [ { "upto": 15, "price": 4.0 },
                                            { "upto": null, "price": 7.6 } ] },
  "steam": { "rateType": "flat", "fixedPrice": 268 }
}
```

- `rateType`：`tou` 分时 / `flat` 单一制 / `tier` 阶梯 / `tier_tou` 阶梯+分时
- **可选的计价方式由品种决定**，不是四个都能选：电能四种都支持，
  水表 / 燃气支持 `tier` + `flat`，蒸汽只支持 `flat`。
  来源是字典属性 `support_rate_types`（在「品种指标」页可见）
- 阶梯要有档位（`upto` 留空 = 不封顶）；分时至少一个档位；单一制必须有 `fixedPrice`
- **填了价格就算开通，清空就算停用** —— 没有独立的「开通」勾选框

租户级仍保留 4 份 `rate_template`，但**只作为「填入示例价」的参考**，
不再是必选来源，也不出现在场站费率页的可选项里。

写接口：
- `POST /api/energy/org-rate` —— 组织费率（客户能写自己的组织；越权返回 403）
- `POST /api/energy/customer-rate` —— 客户兜底（租户传 `customerId`）

结构不合法（分时无价、单一制缺价、阶梯无档、非法 `rateType`）返回 400，不会落库
—— 避免算账时才发现是脏数据。

#### 空闲时段：班次和默认工作时段，只有一套生效

服务端判定的优先级：

```
单日排班 daySchedules   （人工例外，最高）
批量规则 batchRules      （按 priority 取首条命中）
班次模板 shiftTemplates
默认工作时段 workStart / workEnd   （兜底：没配任何班次时才用）
```

**一旦配了班次，默认工作时段那两个时间框就不生效了** —— 服务端从班次解析出
当日生产时段后就不再读它们。

**所以这两样放在同一页**：默认工作时段就在「场站日历配置」页的月历下方。
配了班次之后，那两个时间框自动标灰禁用，上方出提示说明
「已被班次覆盖，要回到早八晚五请把班次清空」。

> 早先默认工作时段在另一个页签，改完保存、看板毫无变化，很难发现是被班次覆盖了。
> 现在物理上就在一起 —— 见得到班次，也见得到兜底值，配不错。
> 这属于「静默失效」类问题，和删掉的场站告警规则、只存不用的用能等级同一类，
> 处理原则一样：**要么让它生效，要么明说它不生效**。

#### 空闲时段的三个内部页签

| 页签 | 内容 |
| --- | --- |
| 场站日历配置 | 按月看日历，逐日标工作日/节假日/调休；可套内置班次模板（三班/两班/白班）或自定义当天班次。**页面下半部是「默认工作时段」**（没配班次时的兜底） |
| 基线与阈值 | 闲时基线（画看板曲线用）、两个超标阈值 |
| 定时报表 | 报表周期与接收人 —— **二期才自动推送**，现在只存配置 |

两个阈值的含义：

- **闲时待机功率阈值（kW）**：闲时段平均功率超过它 → 判为超标
- **闲时能耗占比阈值（%）**：闲时电量占总电量比例超过它 → 判为超标

`0` = 不判定该项。任一超标即标记，结果写成设备的 `idle_exceed` 时序（1/0），
由设备档案上的计算字段「闲时能耗超标」转成告警。

#### 设备拓扑：它是「一个场站的结构图」，不是组织树

**定位先说清楚**（这一条容易误会）：

- 拓扑**从场站开始向下**画：场站 → 分项/区域 → 设备
- **组织与子组织不进图**。组织层级在「组织与场站」页面看，那里才是完整的
  客户 → 组织 → 子组织 → 场站 树

为什么不做进来：每个拓扑对象在创建时**强制绑定一个场站**（`siteId`），
`update` 时还明确规定「场站不可改」。如果硬把组织塞进来，
设备过滤仍按那个场站的 `siteId` 走，就会出现「结构上有两个场站、
设备只有其中一个」的半截图。

**图的生成方式是「实时投影」，不是快照**：

| 动作 | 是否自动 |
| --- | --- |
| 拓扑对象（那张图本身） | **手动**。点「新建拓扑」选场站和视图，不会因为新建场站而自动出现 |
| 图里的节点与连线 | **自动**。每次打开都重新遍历实体的 `Contains` 关系 |
| 新加的分项 / 设备 | **自动出现**（只要挂在场站子树下），不用「同步」 |
| 拖动节点摆位置 | 手动，坐标存在拓扑资产上，不影响数据 |
| 拉一条线 / 删一条线 | **改的是真实关系**。见下 |

**连线 = 改数据**：拓扑里画一条线，写的是 `relation` 表的 `Contains` 关系。
反过来也成立 —— 在设备管理里改了归属，拓扑刷新就变。
不存在「只改图不改数据」的模式。所以画线前要清楚：这会改变实体的从属结构。

约束四条：只支持 `Contains`；不能成环；设备不能当资产上级；
设备 ↔ 场站会自动双写 `additionalInfo.siteId` 与 `SiteContains`。

**设备类型在图上区分**（后端给节点打标记，前端渲染不同图标/标签）：

| 类型 | 判据 | 图上表现 |
| --- | --- | --- |
| 普通设备 | 默认 | 「设备」 |
| 网关 | `additionalInfo.gateway = true` | 「网关」 |
| 虚拟设备 | `additionalInfo.deviceVirtual` = `virtual`/`1`/`true` | 「虚拟表（计算）」 |

**一个场站可以建多张图**，按视图区分：物理结构 / 用电分项 / 用能区域 /
用能性质 / 空间位置。演示数据默认只建一张物理视图。

**设备必须挂在 `Contains` 关系下才能进图** —— 只写 `additionalInfo.siteId`
属性不够（拓扑只走关系遍历，不按属性补）。正常流程不用管：
场站 ↔ 设备连线的接口会双写这两样。

**TB 原生的「资产管理」「设备管理」图标已换成上面三个。**
需要建模时走左侧「实体」菜单，日常运维走这三个 —— 点进去直接是该客户的数据，
不用再选一次客户。

> **这 14 个 `DEFAULT` 项必须与前端对齐。**
> 自定义菜单是「完全替换」语义：一旦绑到租户，侧边栏就只渲染这里列出的项。
> 少列一个，那个顶层菜单就消失。
> 前端默认菜单的权威列表在 `ui-ngx/src/app/core/services/menu.models.ts`
> 的 `defaultUserMenuMap`（`Authority.TENANT_ADMIN` 那一组），改动任一侧都要同步另一侧。
>
> 另外：`DEFAULT` 项只写 `{id: "iot_hub"}` 时，子菜单由前端回落到默认定义展开 ——
> 这就是「明明只写了一行，却能显示完整子树」的原因。

### 两条硬限制

**1. 最多两层。** 侧边栏的 `menu-toggle` 把每个子项一律交给 `menu-link` 渲染，
而 `menu-link` 没有展开能力 —— 第三层点不动或跳到 undefined 路径。

**2. 客户菜单的绑定靠 `customer.customMenuId`，不是菜单的 `customer_id`。**

```
custom_menu.customer_id  →  恒为 NULL_UUID（NOT NULL 约束）
customer.custom_menu_id  →  指向具体菜单 id
```

客户登录时 `findCustomerHierarchyCustomMenu` 的查找顺序：

1. 按 `customer_id` 找默认客户菜单 → 命不中（是 NULL_UUID）
2. 读 `customer.customMenuId` 按 id 找 → **这一步对上才行**
3. 都没有 → 退回 TB 原生菜单

只建菜单不写 `customMenuId`，客户永远看到默认菜单。

## 九、没接 RTU 时怎么造数据（模拟器）

现场板子还没到、或者要复现某个报表问题时，用 `scripts/20-rtu-simulator.py`。
它**按 RTU 的原始代号上报**（`U` / `I` / `P` / `Ep` …），所以顺带能验证
规则链的 key 转换节点是否在工作。

### 为什么不能靠「演示数据」验证抄表

演示数据是一次性写进去的静态序列。生成完几小时后，最后一次遥测已经超过
抄表的「新鲜度窗口」（`STALE_WINDOW_MS = 10 分钟`），于是每次抄表都判
`stale`（设备未上报新数据），台账用量永远是空 —— 看起来像抄表坏了，
其实是数据不新鲜。模拟器能持续上报，这个问题就不存在了。

### 三条命令

```bash
# 1. 看有哪些表
./scripts/20-rtu-simulator.py --base http://127.0.0.1:8090 \
    --tenant tenant@126.com --tenant-pass '12345678' --list

# 2. 给一块表持续上报（每 60 秒一次，共 30 次）
./scripts/20-rtu-simulator.py --base http://127.0.0.1:8090 \
    --tenant tenant@126.com --tenant-pass '12345678' \
    --device '单相园-1#进线总表' --interval 60 --count 30

# 3. 一直跑，Ctrl-C 停
./scripts/20-rtu-simulator.py ... --device '单相园-1#进线总表' --interval 300 --count 0
```

`--device` 支持精确名或唯一的部分匹配。名字有歧义时会列出来让你写全。

### 表底（Ep）是累积值，不要乱跳

模拟器的 `Ep` 单调递增，每轮把「本段用电」加进去。
手上有历史表底时用 `--seed-reading` 接着往上跑；
如果种子比库里已有的表底**小**，抄表会判「电量倒走」为 abnormal（这是对的，不是 bug）。

### 网关模式：与真实 RTU 走同一条路

```bash
./scripts/20-rtu-simulator.py ... --mode gateway --gateway 'ED1-Gateway' \
    --device '单相园-1#进线总表' --mqtt-host 127.0.0.1 --mqtt-port 1883
```

它发的就是 `v1/gateway/telemetry`，payload 形如：

```json
{"单相园-1#进线总表": [{"values": {"U": 232.9, "I": 14.55, "Ep": 1305.8}}]}
```

### 现场板子的设备名必须与平台一致

RTU `main.py` 里的两个名字是**编译进固件的**：

```python
GATEWAY_NAME  = "ED1-Gateway"
METER_DEVICE  = "PowerMeter-DDSU777"
SENSOR_DEVICE = "Sensor-HZ8706"
```

网关模式靠**名字**匹配平台设备。平台上叫「单相园-1#进线总表·星河工业园」，
板子上却发 `PowerMeter-DDSU777`，数据会全部丢掉（平台收不到就不会报错，只是没数）。

**上线前对一遍**：

```
平台上的设备名  ==  rtu/main.py 里的 METER_DEVICE
网关设备名      ==  rtu/main.py 里的 GATEWAY_NAME
```

对不上就改 `main.py` 重新烧录；一台网关带多块表时，`METER_DEVICE` 要按表逐台对应。

## 九之一、把设备 / 资产分配给客户

租户建的场站、分项、设备，要挂到客户名下，客户才能看到。两个接口：

```
POST   /api/customer/{customerId}/device/{deviceId}     分配设备
DELETE /api/customer/device/{deviceId}                  取消（归还租户）
POST   /api/customer/{customerId}/asset/{assetId}       分配资产
DELETE /api/customer/asset/{assetId}                    取消（归还租户）
```

只有 `TENANT_ADMIN` 能调；客户账号调用返回 403。

### 取消分配 ≠ 还给原客户

**取消分配是把归属还给租户**（`customer_id = NULL_UUID`），不是还给上一个客户。
要换客户，直接调一次「分配给新客户」即可，不用先取消。

这一点很容易踩：测试时把客户 A 的资产「取消分配」，
结果它变成了租户级资产 —— 客户 A 读不到、看板引用它的地方全 403。
正确做法是 `POST /api/customer/{A}/asset/{id}` 直接还回去。

### 生效是即时的

分配完成后，对方账号**立刻**能读该实体及其遥测，不需要重启。
前提是接口内部走了 `changeEntityOwner`（改组 + 清 `ENTITY_OWNERS_CACHE`）——
只改 `customer_id` 字段会留下旧缓存，表现为「分配成功但对方 403，重启才好」。

## 九之二、抄表的用量口径（账单准不准看这里）

台账和账单上的「用量」是 **账期累计**，不是「最后一次抄表的增量」。

```
账期用量 = (账期期末表底 − 账期期初表底) × 倍率

期初 = 本月第一条记录的 coalesce(prev_reading, curr_reading)
        （首月首抄没有上月表底，就是基线值本身）
期末 = 本月最后一条记录的 curr_reading
```

接口里两个字段都给了：

| 字段 | 含义 | 用在哪 |
| --- | --- | --- |
| `usage` | 账期累计 | 台账、账单金额 |
| `lastUsage` | 本次抄表的增量 | 月内对账、看「这两次之间用了多少」 |
| `periodOpen` / `periodClose` | 期初 / 期末表底 | 核对、审计 |

**为什么强调这个**：一个账期里会抄多次（首抄建基线 → 月中核对 → 月末出账）。
若按「最后一条的增量」算，月末那次抄表只要设备没新增读数，月用量就成了 0，
账单金额跟着变 0 —— 实测踩过：实际 94.575 kWh，台账报 0.0000。

**首月为什么可能没数**：第一次抄表只建基线（`state=first`），没有上月表底就算不出用量。
第二次抄表才开始有数。这不是故障。

**一次 stale 不会把月累计冲掉**：月内某次抄表遇到设备离线（`state=stale`），
最新记录里没有表底。统计层只取「真正抄到表底」的记录算首末，
所以已经算出的月累计会保留 —— 台账上这台表仍显示 `quality=estimated`，
但 `usage` 还是本月累计。展示层和统计层是分开的。

## 九之三、峰谷分析的口径（为什么它和台账能对上）

峰谷分析 `/api/energy/tou-analysis` 每个桶的电量 = **相邻两个整点表底之差**：

```
某小时电量 = 该小时末的表底 − 上一小时末的表底
区间总量   = 末点表底 − 首点表底（与台账的账期累计同一口径）
```

**边界严格按整点对齐**：查询 `from ~ to` 时，只统计「终点落在 `(from, to]` 内」的增量。
所以：

- 传整点（`10-09 00:00` ~ `10-10 00:00`）→ 结果 == 表底首末差，分毫不差
- 传非整点 → 首尾各有一小时的对不齐，总量会有 ≤1 小时粒度的误差（正常）

**验收脚本因此把边界对齐到整点**。手工核对时也这么传，才能对上。

### 表底倒走会告警

换表、表计归零、上报错值时，表底会变小。这种段算不出正增量，
算法会跳过并在响应里给出：

```json
{ "backwardDevices": 1, "backwardSegments": 1,
  "warnings": ["1 台表计出现表底倒走（换表 / 归零 / 上报错值），共 1 个小时段被跳过 ——
                这段时间的用电量未计入，本月用量会偏小或偏大，请核对表底"] }
```

看到这条就说明**这一个月的数不能直接用**，要先确认表底。
不告警的话，页面上是一张正常的图 + 一个错数，查一个月也查不出来。

### 虚拟表不参与峰谷拆分

手工填报的虚拟表（空调、其他水表）一个月只有一个总量，**没有小时分布**。
硬拆峰谷等于编数，所以它不参与计算，响应里会带上：

```json
{ "virtualMeters": 1,
  "warnings": ["1 台虚拟表（手工填报）没有分时数据，未参与峰谷拆分；
                其用量看「用能台账 / 账单」（账单里整月归「平」档并标 touAssumedFlat）"] }
```

看到峰谷全 0 且带着这条警告，**不是漏数**：这台表的用量已经进台账和账单。

## 九之四、总分差为负怎么办（用电层级）

### 演示数据的层级是**算出来的**，不是各自随机

```
末端表   energy[h] = 基准 × 负荷系数 × 确定性扰动
上级表   energy[h] = Σ 下级表 energy[h] × (1 + 未装表率) × (1 + 线损率)
```

所以每一层都严格满足：

```
进线表底增量  =  Σ 各分项表底增量 × 系数
```

实测（2026-10-23，14 天演示数据）：

```
单相园 进线 1,588.31 = (照明 815.02 + 插座 734.17) × 1.0253
三相园 进线 68,108.89 = (车间 62,529.80 + 办公 3,917.46) × 1.0250
       车间 62,529.80 = (空压 30,019.89 + 车床 26,191.72) × 1.1124
```

系数就是配置的线损与未装表：进线 1.025（2.5% 线损），
车间 1.1124（3% 线损 + 8% 未装表）。

### 「总分差」是物理量，不是误差

客户拿进线表底减去各分项之和，得到的差额**应该为正**，含义是：

```
差额 = 线损电量 + 尚未装表的负荷（如空调、公共照明）
```

这个差额在演示数据里是设计好的，不是算错。真实项目里同样存在。

### 差额变成负数 = 表底被覆盖过

如果 `父表增量 < 子表增量之和`，几乎只有两种原因：

| 原因 | 特征 | 怎么修 |
| --- | --- | --- |
| 换表 / 表计归零 | 某台表表底骤降 | 换表要在平台侧重建或重置基线 |
| 手工/脚本写入了较低表底 | 同一时刻出现两个差异很大的值 | 删掉错误点 |

**实测踩过**（2026-10-23）：用模拟器给一台表底已到 6.7 万的车间总表
`--seed-reading 2800`，那一小时的表底被写成 2800，
于是 `min` 被拉到 2800，「车间 64,980 + 办公 3,917 = 68,897 > 进线 68,109」。

看着像演示数据算错，实际是**测试污染**。

### 一句话自查

```sql
-- 应返回空；有输出就是把哪台表改成倒挂了
WITH span AS (
    SELECT v.entity_id, max(v.dbl_v) - min(v.dbl_v) AS delta
    FROM ts_kv v JOIN key_dictionary k ON k.key_id = v.key AND k.key = 'energy_reading'
    GROUP BY v.entity_id
),
edge AS (
    SELECT r.from_id AS pid, r.to_id AS cid
    FROM relation r
    JOIN device pf ON pf.id = r.from_id
    JOIN device cf ON cf.id = r.to_id
    WHERE r.relation_type_group = 'COMMON' AND r.relation_type = 'Contains'
)
SELECT pf.name AS 父表, sp.delta AS 父增量, SUM(sc.delta) AS 子表和
FROM edge e
JOIN device pf ON pf.id = e.pid
JOIN span sp ON sp.entity_id = e.pid
JOIN span sc ON sc.entity_id = e.cid
GROUP BY pf.name, sp.delta, e.pid
HAVING sp.delta < SUM(sc.delta) - 0.5;
```

`08-verify-release.sh` 已把它做成常规断言（「演示用电层级守恒」），
每次发版都查，不用人工盯。

### 用模拟器续数据时不要覆盖历史表底

```bash
# 对：next 值接在库内最新表底之后
./scripts/20-rtu-simulator.py ... --device '单相园-1#进线总表' --seed-reading 2790.18

# 错：给一个比库内最小值还小的种子，min 被拉低，层级立刻倒挂
./scripts/20-rtu-simulator.py ... --seed-reading 2800   # 库内已到 67780
```

`--seed-reading` 传**当前库内最新表底**，不是任意值。

### 空调这类「没装表」的分项

演示数据里「空调虚拟表」是**独立分项**，不进进线表的层级：

- 有实表的分项（照明、插座、动力）→ 走采集，进线表底包含它们
- 没装表的分项（空调、其他水表）→ 走手工填报，按月填数

两者互斥、不重不漏 —— 虚拟表不再当汇总表，否则同一度电会被算两次。
所以核对总分差时，虚拟表不参与。

## 十、出账（用能账单怎么来）

抄表/遥测给出**用量**，费率给出**单价**，出账把两者算成一张账单资产（`type=energy_bill`），
分配给客户。客户左侧「我的账单」看板读的就是它。

### 三件事必须先到位

| 前提 | 检查 | 缺了会怎样 |
| --- | --- | --- |
| 设备是表计 | 设备档案有 `isMeter=true` | 不出账，且不会报错 |
| 设备档案声明品种 | `energyTypeCode` = elec / water / gas / steam | 跳过，原因写在返回的 `reason` 里 |
| 已配电价 | 场站自定义 / 组织 / 客户兜底任一处有该品种 | 跳过，「未配置电价」 |

**全新库不会预置电价**：平台不帮你编一套假价（会被当成真价收钱）。
装完先看「平台自检 → 费率配置（出账前提）」，`MISSING` 就先配电价再出账。
优先级：场站 `siteCustomRates` > 组织 `energyRates` > 客户兜底。

虚拟设备（`deviceVirtual=true`，如空调虚拟表）**同样出账**。

- 用量取「该月手工填报的月首 `energy` 点」，不走遥测差分；
- 返回 `usageSource=manual`；
- 时段制（tou）账单会多一个 `touAssumedFlat=true` —— 人工填的是整月总量，
  没有小时分布，只能整月归「平」档。这是估算口径，不是漏数。

判定依据是 `device.additionalInfo.deviceVirtual`，**不是** SERVER_SCOPE 属性。
早期代码在属性表里查这个键，结果永远查不到，虚拟表被当成实表，
报「本账期读数不足两点」，两台虚拟表因此永远不进账单 ——
客户对出来「账单用量 < 实际用电」，却查不出原因。

台账（用能台账）也会把这批表补成行：用量优先取账单的计费口径，
没有账单时读手工填报值，`quality=manual`。否则会出现「账单有金额、台账看不到这台表」。

### 在页面上出账

租户管理员打开「我的账单」看板，右上角有 **生成账单** 按钮（客户账号看不到这个按钮）。

点一下会：按当前月出账 → 刷新列表 → 顶部提示「新建 N / 更新 M / 跳过 K」。

跳过的一定要看原因 —— 把鼠标停在该表上，或调一次 dry-run 接口看 `reason`。

### 用接口出账

```bash
# 先试算：只算不写，用来核对金额
curl --noproxy '*' -s -X POST \
  -H "X-Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"period":"2026-10","dryRun":true}' \
  http://127.0.0.1:8090/api/energy/billing/generate | jq '{dryRunUsable, skipped, failed}'

# 确认无误后正式出账
-d '{"period":"2026-10"}'

# 看某账期出了多少张、合计多少
curl ... "/api/energy/billing/summary?period=2026-10"
```

返回里每台表一条：

```json
{ "deviceName": "单相园-1#进线总表", "usable": true,
  "usage": "1588.3130", "energyFee": "1266.40", "basicFee": "1600.00",
  "powerFactorFee": "9.50", "surchargeFee": "23.82", "amount": "2899.72" }
```

`usable=false` 的条目一定带 `reason`，**照着 reason 补配置再重跑**即可。

### 用量口径：表底差，不是 sum(energy)

```
账期用量 = 账期末表底 − 账期初表底（× 倍率）
```

和峰谷分析、台账用同一套口径，三个页面的数天然对得上。

不能用 `SUM(energy)`：`energy[t]` 覆盖的是 `(t−1h, t]`，把 `from` 那一小时
（属于上一账期）算进来会多算约 0.18%。

### 基本电费 / 力调电费只计入线总表

`meterLevel`：1=进线总表，2=分项总表，3=回路。

一个场站 11 块表，如果每块都收 1600 元基本电费，账单会比真实电费高一个数量级
（实测 11 × 1600 = 17600 元，而现场只有一个进线户号）。

规则：

- **电度电费 / 附加费**：按用量，每块表各自算（内部分摊用）
- **基本电费 / 力调电费**：只在 `meterLevel=1` 的进线总表上收

非进线表的账单里会带 `siteLevelFeeNote` 说明这一点。

### 汇总也是分层的

台账与账单汇总里，「电力」合计只算进线总表；水/气/汽没有分层，按全部表汇总。

```
电力   11 台表  →  合计 69,697.199 kWh（两块进线之和，不是全部表相加）
```

否则把总表和分表一起加，同一度电算两遍（实测虚高 2.8 倍）。

账单汇总同时给两个数：

- `totalAmount` —— 按进线汇总，**客户实际应付**
- `allMetersAmount` —— 全部分表之和，内部分摊核对用

### 账单号必须带表码

```
BILL-<客户码>-<账期>-<品种>-<表码>
BILL-A74E3EE0-2026-10-elec-A7CDCF20
```

表码优先取设备的 `meterNo`（现场表号），没有就用设备 id 前 8 位。

**不带表码会出大事**：同一客户同一品种的多块表会算出同一个账单号，
后一笔覆盖前一笔。实测 17 台表出完账只剩 4 张（4 个品种各一张）。

### 幂等与凭证冻结

- 同一账期重跑：只更新，不产生重复
- 状态是 `paid` / `void` 的账单：**一个字段都不动**（凭证已冻结），返回 `skipped`
- 缴费期限 `dueDate` 不随重算漂移

出账前把上月账单改成 `paid`，就不会被这个月的重算改坏。

### 三步核对（金额算得对不对）

```bash
# 1. 用量对不对：与表底首末差比
#    台账里「用量」在有账单时显示的就是计费口径，也可直接查账单 usage

# 2. 电度费对不对：Σ(各档用量 × 单价) 应等于 energyFee
#    账单详情里同时给了明细用量和单价

# 3. 四项之和应等于金额
#    energyFee + basicFee + powerFactorFee + surchargeFee == amount
```

第 3 步已做成验收项（`08-verify-release.sh`），每次发版自动校验。

### 出账不动的东西

- 不改抄表记录（账单是算出来的，不是抄出来的）
- 不改遥测
- 不删旧账单（换价重出会覆盖未付款账单，已付款的不动）
